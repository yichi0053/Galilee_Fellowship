# ADR-0023：成員列表與他人的個人資料，頭像一律用姓名首字

**Status**: Accepted

## Context

ADR-0022 做了個人檔案，但那時只有「我自己」看得到自己的資料。
24 人的團契需要一份「現在有誰」的名單，而看到一則貼文時想知道
「這個人是誰」也沒有路徑可走。

## Decision

- `/members` 列出所有 `active` 成員，每人一格直向長方形（頭像加暱稱），點進去看資料。
- `/members/:id` 顯示那位成員的個人資料：暱稱、生日、興趣、喜歡的經節。
  **不含他的貼文**——那是 `memberFilter`，維持在第二期（ADR-0013）。
- 貼文頁的作者姓名連往 `/members/:id`。
- 導覽選單多一列「成員列表」。
- 後台的「成員管理」分頁沿用既有的停權／標記退出，只補上同一套頭像，
  讓兩份名單看起來是同一件事。

**頭像一律是姓名首字的色塊**，包含 `/members`、後台，以及導覽列右上角的退路。

## Consequences

**代價**：

- **列表上沒有人臉。** Google 頭像來自 auth token 的 metadata，
  **只有當前登入者自己的 session 拿得到**；要在列表上顯示別人的，
  就得把網址存進 `room_members`。ADR-0022 刻意沒有那麼做——
  存了就得處理網址過期、使用者換頭像、以及「已退出的人的臉還留在庫裡」。
  對 24 人的團契而言，首字色塊的辨識度確實比人臉差；這是明知的取捨，
  日後要改就是一支 migration 加一次登入時的寫入。
- **`/members` 與 `/member/*` 兩組路由名稱很接近。** 前者是「關於大家」，
  後者是「關於我」（`/member/me` 我的貼文、`/member/me/edit` 我的設定）。
  兩者不會互相吃到——`/member/*` 要求 `member` 後面緊接 `/`，
  而 `/members/x` 那一格是 `s`——但讀程式的人會需要多看一眼。
- **生日只顯示月日。** 年份是比月日敏感得多的個資，而團契想知道的是
  「什麼時候幫他慶生」。資料庫仍存完整日期（`date` 欄位不能只存月日），
  顯示時砍掉——這代表**年份仍然存在資料庫裡**，任何成員用 API 讀得到。
  真要保護就得改存 `(月, 日)` 兩個整數，那會讓輸入介面變複雜。
- **整份名單是特種個人資料。** §8.6：成員名單帶有宗教信仰資訊。
  `members_select` policy 是 `is_active_member(room_id)`，訪客讀不到任何一列，
  頁面也自己先擋一次並說明原因——空白畫面看不出是「沒有人」還是「你沒有權限」。

理由：看到一張照片想知道那是誰，是這個系統最自然的一個問題，
而在此之前它沒有答案。
